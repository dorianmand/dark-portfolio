# LayerOff.ai — Project Instructions

## Project objective

LayerOff.ai is the personal portfolio and professional profile of Dorian Mandzukic, an architect and computational designer.

It is not a consultancy website, agency website, product shop, or service catalogue.

The website may be shared by Dorian's future employers and managers with clients, collaborators, and professional partners. Every design and content decision must strengthen confidence in Dorian's architectural judgment, technical capability, authorship, and professionalism.

The intended feeling is:

* Premium
* Clean
* Professional
* Impressive
* Smooth
* Calm
* Precise
* Architectural
* Editorial rather than commercial

Read `docs/positioning.md` before making significant design, content, or structural decisions. Treat it as the primary content and positioning reference.

## Core positioning

Dorian Mandzukic is an architect and computational designer working across architectural design, parametric systems, applied AI, and digital planning tools.

Architecture must remain the primary identity. Technology should appear as an extension of architectural thinking—not as the main attraction.

Use "Dorian Mandzukic" as the primary identity.

Use "LayerOff.ai" as a secondary portfolio title, domain, or editorial signature. Do not present LayerOff.ai as a company, collective, agency, or software vendor.

Design the website for:

## Homepage direction

The hero explains the site itself first, then the work, then the person. The
wordmark in the header carries the LayerOff title, so the hero does not repeat
it as a heading — the h1 sits on the positioning sentence, and Dorian's name
and role close the block as a signature.

Positioning sentence (the h1):

A portfolio of computational and AI projects for architectural practice.

The body explains the name as a CAD operation — a layer switched off, not
deleted, its information still organising the work — and uses that to frame the
portfolio's subject: the operative structures behind architectural production.

Sign-off:

Dorian Mandzukic
Architect · Computational Designer

This makes LayerOff the portfolio's title rather than a person's byline, which
is a deliberate shift from the earlier person-first hero. It stays within the
rule below: LayerOff is a portfolio title and editorial signature, never
presented as a company, collective, agency or software vendor, and Dorian's
authorship is named on the page.

Recommended links:

## Project accuracy

Never invent features, results, clients, employers, dates, awards, qualifications, project credits, or implementation status.

Use clearly marked placeholders when verified information is unavailable.

### CompAr

CompAr is an AI-supported architectural competition-planning system. It translates competition briefs into structured design strategies, including program analysis, spatial relationships, organizational logic, and initial geometry for further development in Grasshopper.

The architect retains final approval.

Do not claim that CompAr replaces architectural authorship or automatically produces complete competition designs.

### Design Copilot

Design Copilot is integrated with Grasshopper. It connects parametric building controls with Python-based metrics, rule-based feedback, and planned environmental analysis.

Present it accurately as a developing massing and design-control system.

Do not describe it as a finished, complete building-design platform.

### Formwerk

Formwerk supports German building-permit administration. It transfers structured project information into official state forms, checks required fields, and produces completed PDFs.

Do not claim that Formwerk:

* Generates architecture
* Evaluates architectural quality
* Provides legal advice
* Performs legal review
* Replaces professional planning responsibility

## Writing style

Use first person for biography, philosophy, and personal reflections.

Use neutral editorial language for project descriptions.

Prefer:

* "I developed…"
* "My contribution included…"
* "The project investigates…"
* "The system translates…"
* "The work demonstrates…"

Avoid:

* "We help your office…"
* "Our solutions…"
* "Transform your practice…"
* "Unlock the power of AI…"
* "Cutting-edge…"
* "Revolutionary…"
* "Game-changing…"
* "Industry-leading…"
* "The future of architecture…"

Keep copy concise, factual, confident, and restrained.

Do not write generic marketing filler.

## Visual direction

The visual language should combine architectural precision with editorial restraint.

Use:

* Generous whitespace
* A disciplined architectural grid
* Strong but calm typography
* Wide project imagery
* Clear alignments
* Restrained project metadata
* Short, readable text blocks
* Occasional full-width drawings or visualizations
* Consistent image ratios and spacing
* Subtle hierarchy rather than excessive decoration

Suggested palette:

* Warm off-white or light stone background
* Deep ink or charcoal primary text
* Slate secondary text
* One restrained accent colour
* Project imagery as the primary source of colour

Space Grotesk and Inter may be used if they fit the existing implementation.

Avoid:

* Generic SaaS layouts
* Repetitive rounded feature cards
* Excessive glassmorphism
* Neon colours
* Large artificial gradients
* Glowing technology interfaces
* Generic AI imagery
* Robot or brain illustrations
* Dark startup aesthetics
* Excessive shadows
* Decorative elements without purpose

The site should look like a premium architectural portfolio, not an AI startup landing page.

## Motion and interaction

Motion must feel smooth, controlled, and quiet.

Use:

* Subtle image reveals
* Gentle hover transitions
* Restrained page transitions
* Smooth changes of opacity, scale, and position
* Motion that clarifies hierarchy

Avoid:

* Scroll hijacking
* Aggressive parallax
* Noisy cursor effects
* Constant looping animation
* Large elastic movements
* Animations that delay access to content

Respect `prefers-reduced-motion`.

Animations must not reduce usability or performance.

## Technical workflow

Before changing code:

1. Inspect the repository structure.
2. Read this file and `docs/positioning.md`.
3. Inspect the existing design system, components, routes, and dependencies.
4. Read the available scripts in `package.json`.
5. Preserve useful existing architecture and assets.
6. Identify the smallest coherent implementation approach.

Do not replace the framework, styling system, or component architecture without a clear technical reason and explicit approval.

Do not add dependencies when the existing stack can solve the problem cleanly.

Prefer:

* Reusable components
* Central design tokens
* Consistent spacing and typography
* Strong TypeScript types where TypeScript is used
* Small, focused files
* Clear naming
* Data-driven project content
* Optimized responsive images
* Maintainable CSS
* Semantic markup

Avoid:

* Huge page components
* Duplicate CSS
* Inline magic values throughout the codebase
* Unnecessary abstractions
* Unnecessary packages
* Premature backend complexity
* Placeholder content presented as final content

## Working behaviour

For small, clearly defined changes, implement them directly.

Before a major redesign or architectural change:

1. Briefly describe the intended approach.
2. Identify the main files or components affected.
3. Explain any meaningful trade-offs.
4. Then implement the change unless a missing decision would materially alter the result.

Do not repeatedly ask for confirmation about minor visual details. Make restrained decisions consistent with this document.

Preserve existing user content and unrelated work.

Do not delete assets, pages, or components unless they are confirmed to be obsolete or the task explicitly requires removal.
